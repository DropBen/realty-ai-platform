# Acceptance criteria and implementation state

This document is a release checklist, not a production-readiness certificate. “Implemented” means executable backend and UI behavior exists. Automated provider contracts use controlled HTTP responses; they do not certify live services. See [verification evidence](verification.md) for commands actually run.

| Subsystem | Acceptance criteria implemented | Evidence / remaining acceptance |
|---|---|---|
| Authentication and tenancy | Register/login/logout; hashed passwords and sessions; organization memberships/switching; five centrally enforced roles; session-bound CSRF; tenant filters on queries and writes; composite tenant foreign keys | API/security tests. Email verification, password recovery and MFA are release gates before public signup. PostgreSQL isolation/load testing remains required. |
| Relational CRM | Validated paginated/sorted contact, lead, buyer, seller, property, deal, task, appointment and transaction APIs; editable forms; archived contacts; confirmed preferences; activity/audit history | API tests cover creation, input validation, scoped reads/writes and foreign keys. Browser journeys cover contact/preferences/timeline. Seller offers and milestones use deals/transactions; no MLS feed or e-signature integration. |
| Client context | Profiles combine preferences, source facts, communications, activities, tasks, appointments, commitments and property matches; unknown values stay unknown; manual and extracted facts differ | Extraction and matching tests. Profile context is bounded to 30 rows per source type and 100 active properties. Dedicated exhaustive search/indexing and calibrated lead scoring remain future work. |
| Briefing and command center | Counts, agenda, overdue tasks, follow-ups and pipeline come from tenant records; organization timezone defines the day; structured budget/location/contact recency queries; meeting preparation; configured AI answers cite allowed sources | Service/API tests; browser command journey. Structured query grammar is deliberately bounded. Open-ended language requires configured AI and is not presented as unlimited search. |
| AI provider and evidence | Provider protocol; bounded tenant context; strict response schemas; literal evidence verification; no execution tools; recorded usage/quota; proposed CRM changes require review | Invalid output, timeout and source-evidence tests. Bulk external approval is intentionally absent. Uncertain external delivery requires human reconciliation. |

Docker daemon and Azure CLI/subscription were unavailable on the build host. PostgreSQL, container, browser and Azure execution cannot be marked passed from file creation. |

## Production release gates

1. Run all CI jobs, inspect browser screenshots/traces, and fix any failures. Add accessibility and realistic multi-user PostgreSQL/load testing.
2. Validate Google consent and mailbox/calendar contracts, Stripe test-mode lifecycle, OpenAI extraction/answer evaluations and Blob access in an isolated staging environment.
3. Add account verification/recovery/MFA; commission an independent authorization, upload and AI threat review. Restrict public registration until those controls are accepted.
4. Provision private Azure resources; compile/preview IaC; run a controlled migration; deploy an immutable image; verify TLS, secrets, quotas, alerts, backups and a restore drill.
5. Set operational retention, support, incident response and release/rollback ownership. Enable production only after a documented approval.

The repository can be extended without replacing its tenant model, provider contracts or action boundary. The future items above are deliberately visible instead of being represented by successful-looking placeholder buttons.
