# AI architecture

`AIProvider.structured` is the provider boundary. `OpenAIProvider` uses the Responses API, disables provider-side response storage and requests strict JSON schema. Pydantic revalidates the result after transport. Prompts, bounded retrieval, invocation, source validation and side effects are separate concerns. The implementation follows [OpenAI structured-output documentation](https://developers.openai.com/api/docs/guides/structured-outputs).

## Modes

1. Structured search and briefing always use real records. Search supports named client preparation, buyer/seller/lead categories, budget thresholds, location, stale-contact windows, intent scores and upcoming showings. This is a bounded query language, not arbitrary SQL generated by an LLM.
2. Demo extraction uses conservative patterns for explicitly stated budgets, bedroom counts and commitments. It is labelled `demo_rules`; no remote call or invented answer occurs.
3. With `AI_PROVIDER=openai`, extraction, open-ended answers and document summaries use the configured provider. Missing configuration fails visibly. Follow-up drafting currently uses editable templates from actual contact/conversation context, rather than claiming a model wrote the template.

Every extracted fact keeps its source, exact quote, field, confidence, method, timestamp and verification state. Quotes must be literal source substrings. A proposed preference does not change the confirmed preference row until reviewed. Unknown preferences stay unknown. Inference is not proof: humans verify material facts.

## Actions

The action registry validates typed payloads for CRM updates, task creation, external email and Calendar create/update/delete. Pending suggestions can be edited, rejected or snoozed. Approval checks role, version and expiration, then records a payload hash and creates a durable job in the same transaction. A worker rechecks current membership and the snapshot. Tasks/CRM changes support guarded undo; external communication does not.

The worker records successful outcomes in the timeline, audit and usage tables. Uncertain external results are never resent automatically. An operator must inspect the provider and reconcile the result before preparing another action. Review outcomes are retained for future evaluation; no automated model retraining is claimed.

## Limits and extensions

AI usage charges attempted calls before transport and tracks returned token totals. Billing locks serialize quota reservation per organization on PostgreSQL. Structured search returns at most 50 records; meeting preparation uses bounded recent context and property candidates. Broader semantic retrieval, conversation memory beyond these records, calibrated learned intent scoring, relative-date interpretation, visual workflow editing, call transcription and OCR are future extensions.

Specialized email, calendar, property and document behavior is represented by explicit services and job kinds. No general-purpose autonomous agent is allowed to invoke arbitrary tools or bypass approvals.

## Evaluation and evidence hardening

Extracted values must be supported by their exact source quote, including numeric shorthand such as 650k. Nearby but different amounts are rejected. Commitment titles derive from the quoted promise and remain proposed until an authorized person confirms an owner/deadline. Document entities keep exact value/quote/source identity; classification requires review with the current document hash. Summaries remain unverified analysis.

Usage totals reject malformed, negative or extreme token counts. Quota reservations serialize in PostgreSQL and SQLite before transport; invalid evidence/schema stops a job without five repeated paid attempts. `evals/cases.json` plus `scripts/evaluate.py` provide 20 offline adversarial/regression cases; this does not assess live model precision or safety against every possible prompt.
